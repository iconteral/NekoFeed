### Slide 1: 自我介绍与项目概览 (1.5分钟)

`【动作指引：翻到 Slide 1，展示 NekoFeed 的系统架构图】`

各位面试官下午好，我是本次汇报人。今天我分享的项目是 **NekoFeed**，这是一个基于 Jetpack Compose 的高性能 AI 智能辅助信息流客户端系统。

作为一个 Kotlin 的初学者，在做这个项目的过程中，我的核心目标不仅是完成业务功能的开发，更是为了攻克信息流场景下的性能顽疾。因此，我在项目的底层设计上采用了 **MVVM 架构模式**，严格遵循**单向数据流（UDF）**的设计原则。

大家可以看一下屏幕上的架构图：
* 我们的前端 UI 基于声明式框架 **Jetpack Compose**，所有的 UI 组件通过订阅来自 **FeedViewModel** 的 `uiState` 状态流进行局部刷新。
* ViewModel 通过 API 提供者动态地与基于 **Retrofit + OkHttp** 的网络层进行通信，获取服务端的数据。
* 同时，为了应对断网、离线体验和本地轻量级 AI 分析的需求，我们利用 **Room 数据库** 做结构化缓存，并用 **DataStore** 存取轻量级开关配置。

本项目的业务突破点，在于针对信息流中**文章、视频、商品、广告等多样式卡片混排**进行高效分发，并在高频互动下使用**乐观更新**技术，提供无感的点赞收藏体验。下面，我将从技术选型、组件分发、重组优化、广告曝光埋点、网络层设计、多媒体缓存六个方面，详细拆解我们的实现思考。

### Slide 1.5: 核心技术选型与实现思考 (2.0分钟)

`【动作指引：翻到 Slide 1.5，展示四大技术选型对比表】`

在项目立项之初，我对行业内常用的几种方案进行了深入对比，并没有盲目跟风，而是基于“工程实用性”做出了如下选择：

第一，在 **UI 渲染**上，传统 XML 配合 RecyclerView 稳定但模板代码太重，每多一种卡片就要写一套 Adapter。而 **Jetpack Compose 声明式 UI** 抛弃了复杂的适配器绑定，直接用 Kotlin 写 UI，使得混排列表的拼接极其高效。因此，我选用了 Jetpack Compose。

第二，在 **异步线程与数据流**上，RxJava 学习曲线陡峭且包体积大，而 Java 原生线程池切线程极其繁琐，稍有不慎就会在主线程发生网络阻塞。**Kotlin 协程与 Flow** 是 Kotlin 的原生法宝，能让我们用写同步代码的方式写网络请求，且能自动绑定生命周期。因此，我选择了协程和 Flow 方案。

第三，在 **本地持久化**上，SharedPreferences 在 Activity 销毁时会在主线程进行同步磁盘写入，大文件写入时极易引发 ANR 卡死。而 SQLite 手写 SQL 语句容易拼错闪退。我选用了 **Room 数据库配合 DataStore**，Room 负责结构化分析数据，DataStore 负责轻量配置，且都在子线程读写，彻底杜绝了主线程阻塞。

第四，在 **网络层**上，原生 HttpURLConnection 太原始，我选用了业界标准的 **Retrofit + OkHttp**，利用拦截器自动注入 Token，并针对“动态切换域名”的业务痛点进行了小幅封装。

### Slide 2: 归一化模型与多样式卡片路由 (1.5分钟)

`【动作指引：翻到 Slide 2，展示 FeedItem 数据结构和 when 路由代码截图】`

在混排信息流中，不同类型的卡片（如普通的图文卡片、电商商品卡片、包含视频播放的媒体卡片）在服务端下发的 JSON 中数据结构往往千差万别。如果让客户端为每种类型写一套独立实体类，不仅转换代码混乱，还容易在 null 安全上翻车。

为解决这个问题，我们进行了**数据模型归一化**：
* 所有的卡片数据，在网络反序列化时，统一映射为单一的 `FeedItem` 实体类。
* 我们根据它的 `itemType` 和 `cardType` 字符串，通过 Kotlin 的 `enum class` 进行安全解析，得到强类型的卡片枚举 `FeedCardType`。
* 在 UI 入口组件 `FeedItemCard` 中，使用 `when` 条件分支进行路由，自动将数据路由至 `LargeImageFeedCard`、`SmallImageFeedCard`、`VideoFeedCard`、`ProductFeedCard` 等独立的卡片组件中。

这里有一个性能优化的细节：在 Compose 编译器中，如果一个类内部包含 `List` 等集合，编译器会默认将其标为“不稳定类型”，每次重组都会强制重绘该子组件。为此，我们在 `FeedItem` 数据类上强制加上了 **`@Immutable` 标记**。这相当于跟编译器签订了“绝不修改”的协约，使得所有未修改的卡片在滑动重组时都能被完美“Skip（跳过）”，列表滑动因此极为顺畅。

### Slide 3: Compose 重组性能优化 (1.5分钟)

`【动作指引：翻到 Slide 3，展示局部重组与 Layout Inspector 优化前后的对比图】`

在声明式 UI 中，解决“无谓重组引起的卡顿”是决定应用能否上线的关键。我们采取了三项细粒度的重组优化手段：

第一，**状态流的细粒度拆分**。在视频播放时，播放 ID（`playingItemId`）是随滑动不停改变的。如果把它混在整体的 `uiState` 里，整个页面所有卡片都会跟着重组。我们把 `playingItemId` 拆成独立的 `StateFlow`。改变时，只有受影响的卡片组件会局部重组，其他几十个卡片直接 Skip。

第二，**利用重组作用域限制与稳定的 Key**。在 `LazyColumn` 渲染中，我们显式传入了稳定的 `key = { it.id }` 以及正确的 `contentType = { it.cardType }`。当列表上下滚动复用行时，Compose 能够复用相同类型的卡片节点，避免了全量重新创建视图的开销。

第三，**Lambda 闭包引用缓存**。我们在 UI 传递点赞、收藏回调时，使用 `remember` 缓存了 Lambda 回调。这样，即便父组件重组，子卡片拿到的 Lambda 引用地址保持一致，不会判定为“参数改变”从而发生二次绘制。

根据 Layout Inspector 测试，优化后，滑动重组红框极少发生，帧率稳定在 60 帧以上。

### Slide 4: 交易广告核心：50% 视口曝光判定与埋点系统 (2.0分钟)

`【动作指引：翻到 Slide 4，展示“50% 曝光判定示意图”和曝光计算的时序图】`

作为交易广告部门的客户端方向，精确的广告曝光计费是业务核心。曝光多记了属于欺诈，少记了会导致公司亏损。我们在项目中实现了**“50% 视口曝光判定算法”**。

在性能上，我们不能在列表滚动的每一帧都去计算曝光，那样会极大消耗 CPU 算力。我们的优化逻辑是：
1. 使用 `snapshotFlow` 监听列表滚动状态 `isScrollInProgress`。
2. 只有当**滚动完全停止（`false`）时，启动 1 秒防抖延时（`delay(1000)`）**。如果在这 1 秒内用户继续滑动，由于协程被重新收集，上一次延时会被自动取消（Cancel）。
3. 1秒防抖通过后，说明用户在某个卡片上停留了，我们再去读取 `listState.layoutInfo.visibleItemsInfo`。
4. 运用几何公式，计算当前卡片的重叠像素：
   $$VisibleRatio = \frac{\min(Offset + Size, ViewportEnd) - \max(Offset, ViewportStart)}{Size}$$
   如果该比例大于等于 50%，说明卡片展示符合广告有效曝光标准。我们将其记录，并通过内存集合 `exposedItems` 进行同一会话内的去重，最后写入本地 Room 数据库的埋点表中，等待批处理上报。

这样，我们既做到了曝光数据不遗漏，又将原本高频的像素相交计算降低了 90% 以上，完美兼顾了业务准确性与渲染性能。

### Slide 5: 网络层动态配置与高并发控制 (1.0分钟)

`【动作指引：翻到 Slide 5，展示网络层拦截器链与 Semaphore 并发限流代码】`

为了方便开发调试，我们的客户端需要支持“动态修改 Base URL”而无需重启 App。我们通过自定义封装实现了这一需求：
* 我们将 Base URL 和 API 实例变量标记为 **`@Volatile`**。多线程并发读取时，一旦在设置页面更新了域名，其他协程网络请求能够立刻读取到最新的连接实例。
* 已发出的请求通过 OkHttp 底层的 Socket 平滑传输完毕，不会产生中断或闪退。
* 在 OkHttp 拦截器链中，我们通过 Lambda 提供者动态注入 Token，并且拦截 `401 Unauthorized` 状态码，一旦失效即刻回调清除本地登录态并跳转至登录页。

另外，针对 AI 自动获取卡片摘要等后台异步任务，为了防止下拉刷新时数十个卡片并发请求打爆网络线程池和服务器，我们使用了协程底层的 **`Semaphore(8)`** 进行物理并发限流。利用其非阻塞的 `withPermit` 挂起机制，使得多余的请求挂起等待，而不是阻塞物理线程，保证了应用的极佳响应速度。

### Slide 6: 首页 Feed 主逻辑与多媒体异步加载缓存 (1.5分钟)

`【动作指引：翻到 Slide 6，展示图片/视频的加载缓存流水线示意图】`

最后，我来介绍首页 FeedItem 主逻辑以及多媒体的加载与缓存思路：

在**图片渲染**上，我们基于 Coil 库封装了 `SkeletonImage`：
* 滑动时引入 `100ms` 加载防抖延迟，快速滑过不可见的卡片将不会发起图片请求。
* 通过 `.allowHardware(true)` 开启硬件位图加速，让解码直接在显存完成。
* Coil 内部的强引用内存缓存、LRU 内存缓存和本地磁盘三级缓存，能保证已看图片“秒出”。

在**视频播放与缓存**上，我们自研了全局共享的播放器管理器 `PlayerManager`：
* **单例共享**：由于系统硬件解码器稀缺，我们全局仅维护一个 `ExoPlayer` 实例。只有当卡片被算为视口中心播放项时，才通过 `AndroidView` 挂载 `PlayerView`；滑出视口或页面进入 `ON_PAUSE` 后，触发 `DisposableEffect` 释放连接并暂停。
* **物理缓存**：使用 Media3 的 `SimpleCache` 设置了最大 **100MB 的 LRU 本地缓存**。ExoPlayer 播放时，所有的媒体请求都会被 `CacheDataSource` 拦截，优先读取本地视频流文件，没命中则流式拉取网络并同步缓存入磁盘，大幅降低了用户的网络开销与起播等待。
