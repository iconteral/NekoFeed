# NekoFeed 学习总结

## 1. 棘手问题与解决方案

### 异构数据无法直接驱动统一 UI

RSS、文章、广告、商品和视频字段差异很大。解决方式是把差异收口在服务端归一化层，以 `FeedItem + item_type + card_type` 作为跨端契约。客户端卡片只关注稳定字段，扩展新内容不再修改整条链路。

### 点赞和收藏在多个页面状态不一致

早期页面各自修改本地对象，容易出现首页已点赞但详情页未更新，或计数重复累加。最终改为以服务端响应为权威值，并通过 Repository 与 `InteractionSyncStore` 广播结果，列表规则另有 JVM 单测覆盖。

### Compose 列表中的视频资源争抢

每张视频卡创建播放器会造成解码、内存和状态问题。项目改为 `PlayerManager` 复用单 ExoPlayer，以可见项和 `ownerId` 管理播放归属；滚出屏幕后暂停，实际开始播放后才记录 play。

### AI 延迟影响首屏体验

若等待 AI 完成后再展示 Feed，首屏会被网络和模型延迟阻塞。最终采用“原内容先展示、AI 结果渐进增强”的方式，配合并发限制、Room 缓存、加载状态和失败回退。AI 从主链路依赖变成可选增强。

### 曝光统计容易虚高

仅凭 Composable 出现就计曝光，会把预组合和快速划过都算入。当前以可见面积至少 50% 为阈值，并在同一会话内对内容去重；Mock 和真实环境分开统计，CTR 通过纯函数聚合并有单测。

## 2. 踩坑复盘

- Android Emulator 的 `localhost` 指向模拟器自身，访问电脑服务必须使用 `10.0.2.2`。
- 网络 DTO 与服务端 snake_case 不一致时，必须用 `@SerializedName` 明确映射，不能依赖命名巧合。
- 乐观更新若同时修改布尔状态和计数，失败回滚很难保证一致；权威响应更适合本项目规模。
- Compose 中把播放器或网络对象放进卡片生命周期会反复创建，应提升到共享管理器或 Repository。
- 图片、视频和 LLM 都属于不可靠外部依赖，每一层都需要可见的失败状态与降级路径。
- SQLite 启动时手写 `ALTER TABLE` 可以快速迭代，但随着版本增加会失控，正式项目应尽早引入迁移工具。
- Git 历史中存在“大而全”的早期提交，定位回归成本高；后期使用按功能拆分的 `feat/fix` 提交明显更易审查。

## 3. 从 Git 历史看到的迭代

项目在 2026-05-31 至 2026-06-07 共形成 32 个提交和 v1.0.0 至 v1.4.0 多个阶段标签。演进顺序大致为：基础 Feed -> 服务端与用户系统 -> LLM -> Material 3 UI -> 互动修复与视频 -> 对话助手与分析 -> Onboarding -> 分类、标签和播放体验收尾。

这段历史说明功能并非一次生成完成，而是围绕真实问题持续调整。最有价值的变化不是页面数量，而是把互动一致性、AI 延迟、视频单实例和曝光口径从“能演示”推进到“可解释、可测试”。

## 4. 后续改进点

1. 增加服务端 pytest 集成测试和 Android Compose UI 测试。
2. 用 Paging 3/RemoteMediator 完成真正的离线优先分页。
3. 为曝光增加停留时长条件，例如 50% 可见且持续 1 秒，并引入 event ID 防重复上传。
4. 在固定真机上使用 Macrobenchmark 测冷启动、滚动帧耗时和内存峰值。
5. 将 AI 调用全部代理到服务端，隐藏密钥并记录模型耗时、失败率与 token 成本。
6. 为管理后台增加认证、权限、CSRF 和正式数据库迁移。
7. 补充无障碍语义、动态字体、弱网和旋转/进程重建测试。
